# AP68040 build variant

A second build of the core with the [AP68040](https://github.com/apolkosnik/AP68040)
(a pipelined MC68040 with its MMU, caches and FPU) in place of the TG68K and the fx68k.
It is its own core on the card, `apolkosnik.Minimig040`, next to the standard one.
The built core is in `releases/apolkosnik.Minimig040/`: copy it to
`/cores/apolkosnik.Minimig040/`.

The dock's keyboard and mouse come from the handheld firmware fork, which picks the
cores it sends them to by their ID: it has to know the Minimig core's build variants
(see *Keyboard and mouse on the dock* in the main README). A firmware build that knows
only `apolkosnik.Minimig` (the fork before commit `0a58bbbc`) gives this core neither; the handheld's own controls and a
dock controller work with any firmware.

## Building

```
tools/build_variant.sh ap68040          # bitstream and metadata in build/variant-ap68040/core
```

`tools/stage_variant.sh ap68040 <dir>` assembles the variant's source tree, which
`tools/build_variant.sh` builds with the same Vivado 2018.3 flow as the standard core
(`tools/build_vivado2018.sh`). The tree is this repository with:

* `patches/rtl/*.patch` applied: the CPU in `cpu_wrapper.sv`, the CPU clock
  (`gb_clocks.sv` CLKOUT5, `minimig_gamebub.sv`);
* the files of `remove.txt` removed: the TG68K, the fx68k, `cpu_cycles.sv`;
* `rtl/` (the AP68040 and its bus bridge) as `rtl/ap68040/`;
* `src/cpu_cache_new.sv` in place of the controller's CPU cache;
* `metadata/` over the core's metadata.

The simulation runs in the staged tree as in this one: `sim/build.sh` takes the AP68040
when the tree has no TG68K, and `sim/run_tests.sh` runs the 68040's tests (`z3_040`,
`mmu040`, `ram040_z3` and `ram040_z2`, `rtg` with the instruction cache on) in place of
the 68030's.

### The netlist against the RTL

Simulation runs the RTL; the FPGA runs what Vivado made of it, and for this CPU the two
were not the same. The AP68040 connects a few signals to instances before the line that
declares them. Quartus and Verilator take the later declaration; Vivado 2018.3 does so
only at a module's top level, and inside a generate block it makes a separate one-bit net
(`Synth 8-605 same-named implicit nets`, `Synth 8-3295 tying undriven pin ... to constant
0`) without an error. The instruction cache's fills were written to set 0 only (`m_pa`,
`m_way`) and the ATCs to way 0 only (`wway`): every simulation passed, DiagROM (caches
off) ran on the FPGA, and Kickstart stopped at a black, yellow or red screen as soon as
it switched the instruction cache on.

* `tools/decl_before_use.py` finds such signals and moves their declarations ahead of the
  first use. `tools/import_ap68040.py` applies it to what it imports (31 signals, 23
  declarations); `tools/build_variant.sh` checks the staged CPU and the port's own files
  before Vivado runs and stops if one is left.
* `sim/gls/run_cpu_gls.sh <staged tree> <trace> ...` (Vivado 2018.3 and its xsim)
  synthesizes `ap68040_minimig` (the core, its FPU and the bridge) out of context, as
  the build does, and replays traces of the RTL simulation on the netlist: the inputs
  before every CPU clock edge go to the netlist, and each of its outputs must be the
  RTL's at every clock. A trace comes from the staged tree's simulation, e.g.

  ```
  sim/obj_dir/Vtb_top --kick asm/crashtest.rom --ms 600 --set 1048=4 --set 104C=8 \
      +cputrace=crash.trc +cputrace_n=60000      # clocks after the reset
  ```

  Without the fix the netlist leaves the RTL at the instruction after `MOVEC D0,CACR` of
  `crashtest.rom` (the instruction cache on). With it, no clock differs in the nine traces of the last run (2026-11-18): all of
  `crashtest.rom`, the first 600,000 clocks of `systest.rom`, `mmu040test.rom` and
  `romtest.rom`, 400,000 of `ramtest040.rom`, 300,000 each of the data cache's copy and
  write benchmarks and of the MOVE16 one, and the first million clocks of Kickstart 3.2
  (none of them runs the FPU).
  Run it after every change of the core or of Vivado's version; about 1000 clocks a second
  for each trace.

## Sources

`rtl/` is generated by `tools/import_ap68040.py` (see `UPSTREAM.md`): AP68040's `rtl/` at a
pinned commit, and the bus bridge of the AP68040 port of Minimig-AGA_MiSTer
(`ap68040_minimig.sv`, `ap040_bus16_adapter.v`, `ap040_bus_timeout.v`), with
`patches/import/*.patch`:

* `0001-xilinx-ram-inference.patch`: the RAM primitives as Vivado 2018.3 infers them. As
  written for Quartus, the data cache's byte-enabled RAM (a three-dimensional array) and
  the tags' true dual port RAM (both ports written in one process) were built from
  registers: 55,000 LUTs. Their 64-word arrays are now LUT RAM (a 128-bit line in block
  RAM takes two 512-word RAMs for 64 words): 32,000 LUTs and 11 block RAM tiles.
* `0002-bridge-gamebub.patch`: the Zorro III board's base in this port's 16 MB units,
  the Kickstart ROM cacheable (read only to the CPU, loaded before it starts), and
  AP68040 main's top level (no VBR / CACR / cache maintenance outputs: the NMI vector
  is taken at VBR 0).
* `0003-adapter-long-word-line.patch`: the adapter offers an aligned long word in one RAM
  transfer, as the TG68K does (`long_cand`, `data_write_lo`; completed with `long_ack`,
  both words move: `data_in_hi`, `data_in`); takes a line as one request (`mem_line`,
  `mem_wline` / `mem_rline`): its four long words back to back from the one asked for,
  wrapping in the line, or the whole line in one RAM transfer when the RAM port answers
  it (`line_cand` / `line_ack`, `data_in_line`); and after a sub-cycle on the RAM port
  (`ram_port`) presents the next one on the same clock edge, as the TG68K does (the RAM
  port lowers its chip select for a controller clock there); elsewhere (the chip bus)
  the sampled IDLE cycle between sub-cycles stays.
* `0004-bridge-line-burst-posted.patch`: line transfers as bursts (TBI negated), each one
  request to the adapter (a read's four beats on four bus clocks once the line is in, a
  write's beats acknowledged as they are collected); the request raised in the bus
  clock of TS, from the bus itself; writes to the fast RAM, lines included, posted (TA
  at once, the next transfer waiting on the bus until the adapter is done; a bus error
  on a posted write is not reported).
* `0005-chip-ram-code-in-the-instruction-cache.patch`: the core's fetch unit takes a
  request to invalidate a line of the instruction cache (or all of it) beside the bus
  snooper's and handles it the same way (`xi_inv`; the core's ports `xinv_req`,
  `xinv_pa`, `xinv_all`, `xinv_done`); the bridge lets chip RAM's code into the cache
  and sends the writes to chip RAM there (see below).
* `0006-cartridge-code-in-the-instruction-cache.patch`: while a cartridge is fitted
  (`ar_on`) the bridge lets its code into the instruction cache (HRTmon's memory at
  `$A00000`, the Action Replay's ROM at `$A80000`-`$ABFFFF`), and takes every line out
  of the cache at a reset and when the Action Replay's control register (`$A80000`) is
  written, so that the cartridge sees the first instruction fetched outside it.

## How it is connected

* The AP68040 runs at 56.77 MHz (MMCM CLKOUT5, twice `clk_sys`, edges aligned).
  `ap68040_minimig` answers its 68040 bus: every transfer becomes one request to
  `ap040_bus16_adapter`, which runs it on `clk_sys` as 16-bit sub-cycles of the TG68K's
  bus contract, so `cpu_wrapper`'s decoding, the chip bus, the RAM port and autoconfig
  stay as they are. A line is a burst and one request: the adapter runs its four long
  words without returning to the bridge between them.
* The Zorro II / III fast RAM and the Kickstart ROM are cacheable, and chip RAM's code
  (TCI on every other transfer: chip RAM's data, which changes under DMA, the registers,
  the RTG memory).
* Chip RAM's code is in the 68040's instruction cache, and every write to chip RAM
  takes its line out again. A 68040 does not keep a line it is told not to cache at
  all: with TCI every long word of code is a line transfer of its own (MC68040UM
  5.7.1), fourteen for a 28-byte loop, and code in chip RAM ran at a fortieth of its
  speed from ROM. Now the bridge negates TCI for code accesses below 2 MB (while the
  fetches there are the RAM's own: `cpu_wrapper`'s `turbochip_d`, off under the ROM
  overlay), and tells the core of the writes its bus does not show it as another
  master's: its own write transfers to chip RAM as they start, and every write the SDRAM
  controller makes there (`gb_sdram_ctrl`'s `chipwr_tgl` / `chipwr_line`: the chipset's
  DMA, and the CPU's own again as it lands). The core's `xinv` port (patch `0005`)
  invalidates the line as a snooped write does: after a fill that is under way, and
  with the refetch of everything the front end had run ahead into if the line was
  there. Only writes into a 128-byte block that has given the cache a line are passed
  on (a map of chip RAM in a block RAM, kept over a reset as the cache's lines are),
  through a queue of eight; should that overflow, every line goes. So old programs that
  change their code in chip RAM without a word to the CPU run, and at the 68040's speed.
* The wrapper's configuration is the 68030's (a 32-bit address bus, Zorro III RAM and
  the RTG board offered). The adapter marks a long word transfer as the TG68K does
  (`longword`), so with the AGA or ECS chipset a long word in chip RAM is one 32-bit
  chip bus cycle, as on the 68030 (the write's first word is held for it, the read's
  second word answered from it). The 68EC020 instruction cache and the cycle throttle are
  off. A transfer nothing answers in 2^20 clocks ends with a bus error.
* No such 32-bit cycle while the Kickstart ROM overlays chip RAM after a reset (patch
  `0009` of the core). The SDRAM has a long word's second word only for chip RAM, and
  the 68040 reads its start address at 4 as one long word: its low half was the low
  word of whatever long word the CPU had read from chip RAM last. That is 0 after the
  core's start, and a ROM entered at its first byte still starts (`$1114`, then its
  `JMP`); after any reset of a running Amiga the CPU started somewhere in the ROM. The
  68030 reads its start address as two words (only its initial stack pointer came out
  wrong, and nothing uses that). `vector` in `sim/run_tests.sh` tests it.
* An aligned long word to the fast RAM, the RTG memory or (fetched) from the Kickstart
  ROM is one transfer, as the 68030's (`long_cand` / `ramready_l`, patch `0008` of the
  core): the SDRAM controller's write buffer takes both words and writes them in one
  slot, and a read is answered with both.
* The SDRAM controller in this variant (`gb_sdram_ctrl` with `CPU_LINE16` and `WQN=8`):
  * the CPU's writes queue, eight entries: a write (a line's four long words too) is
    acknowledged as it is queued, the queue drains in the CPU's write slots, a CPU read
    goes ahead of the queued writes and waits only for a queued write in its 16 bytes;
  * a CPU read of SDRAM chip 1 (the Zorro III RAM, the RTG memory) takes the 68040's
    whole 16-byte line in one slot (two READs, eight words);
  * the cache in front of it (`src/cpu_cache_new.sv`, in place of the controller's CPU
    cache) keeps the last line read, answers a line read whole from it (or at the end
    of the burst), and reads the next line ahead into one of two read-ahead buffers (a
    copy's source and destination are two streams) in chip 1 slots nothing else wants:
    a stream's next line is answered in about 2 `clk_sys` periods instead of 11. CPU
    and chipset writes drop what they meet. From chip 0 (the Zorro II RAM, the ROM) a
    burst brings 8 bytes, two a line, and nothing is read ahead.
  * chip RAM's code has a cache there too, 512 lines of 16 bytes in block RAM, behind
    the 68040's own (above): for the lines that one has lost again, and for a CPU whose
    instruction cache is off. The CPU's fetches from chip RAM come through this port
    (`cpu_wrapper`'s `sel_chipram`, as the TG68K's), and a line of chip RAM is two
    bursts of SDRAM chip 0 in the slots the chipset leaves, 24 `clk_sys` periods
    (0.86 us) on average. A line enters the cache when both its halves have been read
    with no write meeting them and leaves it with any write to chip RAM that has its
    index, the chipset's or the CPU's (the snoop the TG68K's cache has); a line that is
    there is answered whole, in 3 `clk_sys` periods. `sim/sdr` tests the cache under the
    chipset's writes, `sim/gls/run_sdr_gls.sh` the same on the netlist.
  * Andromeda's Nexus 7 showed what chip RAM code cost before the two: its code is in
    chip RAM, it switches the instruction cache on, and it plays its first scene (an
    animation and the music) in the vertical blank interrupt while the main program
    unpacks the next one and then waits for exact music positions. From its load to
    its first picture it took 10.3 s where the 68030 core takes 2.3 s, and the interrupt
    took the whole frame (22 % on the 68030), so the main program never got to its wait
    and the scene stayed for ever. With the cache in front of the SDRAM alone: 4.0 s and
    a third of the frame; with chip RAM's code in the 68040's instruction cache: 2.8 s
    and 27 %.
* A line the bridge inhibits (TCI: chip RAM, registers) is still read whole, over the
  chip bus: mark such memory noncacheable (MMU, TTRs), as 68040 setups do.
* The top level takes the 68040's configuration whatever the menu's CPU setting says
  (`cpucfg_m`): the RAM port's chip select must drop between the adapter's back to back
  sub-cycles, as it does for a 32-bit CPU.

## Limitations

* Speed against the 68030 core (`sim/bench.sh` in each tree: 16 KB passes over Zorro III
  RAM per 100 ms of the simulation, the instruction cache on; computing loops in rounds):

  | | 68030 | 68040 | |
  |---|---:|---:|---:|
  | ALU loop | 173 | 367 | 2.12 |
  | loads and stores in a 256-byte buffer | 81 | 161 | 1.99 |
  | long reads, data cache on (copyback) | 86 | 181 | 2.10 |
  | MOVE16 copy (16 KB units) | 70 | 128 | 1.83 |
  | long writes, data cache off | 115 | 126 | 1.10 |
  | long copy, data cache on | 70 | 76 | 1.09 |
  | long reads, data cache off | 86 | 86 | 1.00 |
  | long writes, data cache on (each line read before it is written) | 115 | 111 | 0.97 |
  | long copy, data cache off | 70 | 50 | 0.71 |
  | a delta animation's player run from chip RAM | 58 | 43 | 0.74 |
  | the ALU loop run from chip RAM | 173 | 367 | 2.12 |

  With the data cache off every load waits for its transfer: the AP68040 takes about 11
  of its clocks from a load's TA to its next transfer (its miss path; none of its build
  options shortens it), the TG68K none, so a copy loop with the data cache off stays
  behind. Kickstart's ROM before exec enables the instruction cache runs slower than on
  the TG68K too.

  Code run from chip RAM is as fast as from the ROM now that it is in the instruction
  cache (the two chip RAM loops did 13 and 9 passes with every line fetched over the
  bus, 38 and 39 with the code cache in front of the SDRAM alone); the animation
  player's two byte reads and two chip RAM writes a round are transfers on the bus,
  which the data cache being off (as that demo has it) and the bridge make slower than
  the TG68K's.
* Code changed in chip RAM and run at once runs as it was: the instructions right
  behind a write are in execution before the write is on the bus. In `smcdist.s` a
  routine called by the very next instruction after the write that changes it runs
  the old code 15 times of 16; with one NOP in between (the 68040's NOP waits for the
  writes) never. Code seven instructions behind its change (`smctest.s`) runs the new
  version: the write takes its line out of the instruction cache and the CPU fetches
  again what it had run ahead into. The 68030 core runs the new code in every case.
* The cartridge (HRTmon or the Action Replay, the main README's *Cartridge*): the
  bridge answers an interrupt acknowledge itself, so the cartridge gets the level 7
  acknowledge as an event (`nmi_ack_toggle`, patch `0010` of `patches/minimig`), which
  arms its vector before the 68040 reads it. That vector is taken at VBR 0: the AP68040
  gives its VBR to nobody outside, and a vector table in fast RAM could be read from the
  data cache. The Action Replay hides at the first instruction fetched outside it
  after its control register is written, and a fetch the instruction cache answers is
  not on the bus: the bridge empties the instruction cache at that write (import patch
  `0006`), so the first instruction outside is fetched (`cart_ar_c` fails without it).
  The cartridge's own code is cached like chip RAM's (the same patch): with the
  instruction cache on, as AmigaOS has it, every long word of uncached code costs the
  68040 a line transfer, and HRTmon took seconds to draw its screen. Nothing but the
  CPU writes to a cartridge, so the cache needs no word of it, as on a real 68040
  (HRTmon flushes the caches itself; the Action Replay's RAM at `$AC0000` stays out).
* On the device: the build with the netlist fix (above) starts Kickstart 3.2 and boots
  from a floppy disk. The start address after a reset (patch `0009`) and the menu's
  Reset (`gb_boot`) are fixed and tested in simulation only so far.
